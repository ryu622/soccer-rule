# 研究計画書
## LLM × 決定木/データ最適化によるサッカー戦術ルールの自動抽出・評価パイプライン
### ―1v1デュエル(仕掛けるvs待つ)判定を対象としたMVP構築―

> 本計画は修士論文(物理情報ニューラルネットワークによる戦術逸脱の定量化)とは別プロジェクトの位置付けである。

---

## 1. 研究背景

### 1.1 定性的な「戦術知識」と定量データの断絶

サッカーの現場(監督・コーチ)が語る「定石」(例:間合いが詰まったら仕掛ける、背後にカバーがいれば待つ)は自然言語で表現される一方、分析の現場にあるのはトラッキングデータ(時系列座標)である。この2つを繋ぐ、解釈可能なルールの構築が求められている。

### 1.2 従来のデータ駆動手法の限界

決定木は「データから閾値を発見する」という点では有効だが、以下の3つの構造的な限界を持つ。

1. **軸並行分割の限界**
   決定木は各ノードで「特徴量Xが閾値t以下か」という、特徴量軸に平行な分割しかできない。実際の戦術判断は「距離が近く、かつ相手の進入角度が浅いときに限り仕掛ける」といった、複数の特徴量の**組み合わせ**(斜めの決定境界)に依存することが多いが、これを軸並行分割だけで近似しようとすると、木を深くして多数の分岐を積み重ねる必要があり、結果として1つ1つの分岐が細切れで意味を読み取りにくいルール集合になる

2. **貪欲な分割による近視眼性**
   決定木は各ノードで「その時点での情報利得が最大の分割」を貪欲に選ぶため、複数ステップ先まで見れば良い分割の組み合わせがあっても、局所最適な分割に引っ張られやすい。「間合い」のような単独では弱い予測力しか持たない特徴量が、「後方サポートの有無」と組み合わさって初めて強い予測力を持つ場合、貪欲法は前者を採用し損ねることがある

3. **特徴量の意味づけを持たない**
   決定木は与えられた生の特徴量(距離、速度など)の数値的な閾値しか出力せず、「なぜその閾値なのか」「その分岐が戦術的に何を意味するのか」という説明を一切持たない。「2.8m」という数字自体は、それが「間合いを詰められた」という意味を持つのか、単なる過学習によるノイズなのかを木は区別できない

**LLMがこれらをどう補いうるか**

- 軸並行分割の限界に対しては、LLMが「距離×進入角度の内積」「相手との相対速度ベクトルの向き」のような**派生特徴量そのもの**をコード内で定義できる。決定木は与えられた生特徴量でしか分岐できないが、LLMは戦術概念(サードマン、カバーリング等)に基づいて特徴量の組み合わせ方自体を提案できるため、決定木が届かない特徴量空間を扱える可能性がある
- 近視眼的な貪欲分割に対しては、LLMが最初から「AかつB」のような複合条件を骨格として一括生成できるため、貪欲法が陥る局所最適を回避できる余地がある
- 意味づけの欠如に対しては、LLMが生成する条件分岐に戦術概念の名前(例:`is_third_man_covering`)を付与できるため、閾値の数値だけでなく「その分岐が何を判定しているか」を人間が読める形で残せる

ただし、これらは「LLMなら必ず優れている」ことを保証するものではなく、決定木に同じ派生特徴量を後から与えるアブレーション比較(3.2節・4節参照)によって、性能向上が実際にLLMの戦術知識由来なのか、単に探索空間が広がっただけなのかを切り分ける必要がある。

### 1.3 本研究の着眼点

「LLMになんでもやらせる」のではなく、LLM(定性・文脈の構造化)とデータ(定量的フィッティング)の強みを分離・連携させたハイブリッドパイプラインを構築する。対象タスクの選定にあたっては、以下の検討を経た。

- 当初案(ハイプレス発動判定)は、判定に使う特徴量(相手との距離)と正解ラベルを機械的な閾値から逆算して作らざるを得ず、循環評価に陥るリスクがあった
- 使用予定データセット(idsse-data、後述)のイベントスキーマを確認したところ、StatsBomb等にあるような独立の「プレス」イベントは存在しない一方、"Tackling game"(1v1の competitive contest)イベントが独立ラベルとして存在することを確認した
- これにより、**1v1デュエル(仕掛けるvs待つ)判定**を第一対象タスクとして採用する。「仕掛けた/待った」のいずれも観測結果に基づく独立ラベルとして扱える

## 2. 研究の目的と仮説

LLMが生成する「ルールの骨格(If-Then構造)」が、決定木(データのみからの分割)に対して

- (a) 性能面(F1スコア)で優位に立てるか
- (b) 解釈可能性の面(戦術概念との対応、専門家からの納得感)で優位に立てるか

の2点を検証する。(a)(b)は独立した問いであり、性能が同等でも(b)の主張は成立しうる。

## 3. 提案手法

### 3.1 タスク定義(第一選択・代替案)

| 優先度 | タスク | 判定内容 | 備考 |
|---|---|---|---|
| 第一選択 | 1v1デュエル | 仕掛ける(TAKE_ON)か待つか | Tackling gameイベントが独立ラベルとして存在 |
| 代替案1 | TakeOn vs Pass | ボールを受けた選手が仕掛けるか繋ぐか | 正例・負例が両方明示的にイベント化される |
| 代替案2 | Clearance vs Pass | 自陣ビルドアップでの選択 | フィールド位置に判断が引っ張られやすい懸念 |
| 代替案3 | Shot vs Pass | ファイナルサードでの選択 | xG/VAEP文脈で研究が多く新規性が薄い |
| 却下 | ハイプレス発動判定 | ― | データセットに独立イベントが存在しないため保留 |

### 3.2 パイプライン全体

```
【定性的な戦術指示・コンテキスト】
        ↓
[ 1. LLM(プロンプト) ] ──> 【ルールの「骨格(If-Then構造)」をコード生成】
        ↓
[ 2. トラッキングデータ ] ──> 【3. パラメータ/閾値のデータ最適化】
        ↓
【4. 評価・可視化】 ──> 決定木ベースライン・強ベースラインとのF1比較 + 解釈可能性の定性評価
```

1. **LLMの役割**:戦術概念(間合い、後方サポート、進入角度等)を理解した上で、実行可能なIf-Then構造のコードを出力する
2. **データ最適化の役割**:LLMが生成したコード内の閾値・定数を、実際のデュエル発生に対するF1スコアが最大になるようフィッティングする
3. **評価**:決定木(max_depth=3程度)に加え、ロジスティック回帰・XGBoost等の強いベースラインも用意し、「性能は強モデルに劣るが解釈可能性で勝る」構図を示せるか確認する

### 3.3 想定される技術的落とし穴と対策

| 課題領域 | 具体的な問題 | 対策 |
|---|---|---|
| 負例の定義 | 「見送り(仕掛けなかった)」はイベントとして記録されない | 機会窓(例:ボール保持開始からTAKE_ONが一定時間発生しない場合)から負例を機械的に構成する |
| データ分割 | イベント単位でtrain/testを分けると同一試合内でリークする | 試合単位(leave-one-match-out)で分割する |
| LLMコード生成 | 生成のばらつき、引数のブレ・実行時エラー | 複数シードでの生成比較、Pydantic/ABCによる型・シグネチャ固定、try-exceptラッパー |
| 座標-イベント同期誤差 | トラッキングとイベントの時刻・座標にズレが生じうる | 事前に該当試合のズレ分布を確認してから特徴量を設計する |

## 4. 使用データ・実装環境

### 4.1 データ

[idsse-data](https://github.com/spoho-datascience/idsse-data)(Hugging Face: `pysport/idsse-data`)を使用する。

- ドイツ・ブンデスリーガ1部/2部 2022/23シーズンの7試合(TRACAB社の光学式トラッキング、Sportec Solutions収集)
- CC-BY 4.0ライセンス、DFL(Deutsche Fußball Liga)の許諾のもと公開
- 出典:Bassek, M., Rein, R., Weber, H., Memmert, D. (2025). *An integrated dataset of synchronized spatiotemporal and event data in elite soccer*. Scientific Data, 12(1), 195.
- 各試合にトラッキングデータ(25fps、全選手・ボール座標)、イベントデータ(パス・シュート・デュエル等)、メタデータ(チーム・選手・ピッチ寸法)が同期して含まれる
- `kloppy`パッケージのSportecローダーで読み込み可能:
  ```python
  from kloppy import sportec
  tracking = sportec.load_open_tracking_data(match_id="J03WPY")
  events = sportec.load_open_event_data(match_id="J03WPY")
  ```
- 利用可能な試合ID:`J03WPY`, `J03WMX`, `J03WN1`, `J03WOH`, `J03WOY`, `J03WPF`, `J03WQF`

### 4.2 前処理・データ確認で先にやること

1. Tackling gameイベントのカラム構成(攻撃/守備ペアの紐付け、座標、時刻、選手ID、result等)を実データで確認する
2. 該当イベントの件数・クラス分布(仕掛けた/待った)を確認する
3. トラッキング-イベント間の同期誤差の分布を確認する(先行文献では平均2.61±3.60m、最大75.35mのズレが報告されている点に留意)
4. 「見送り」負例を構成するための機会窓の定義を確定する

### 4.3 開発環境

- ローカル環境でPython環境を構築し、`kloppy`によるデータ読み込み、特徴量テーブル(DataFrame)作成、決定木ベースラインの実装まではローカルで完結する見込み
- LLMコード生成部分はAPI経由で呼び出す。生成結果の再現性確認のため、複数シード/複数回の生成を比較する運用とする

## 6. 期待される成果

1. LLMが生成する戦術概念ベースの骨格構造が、決定木の軸並行分割では捉えにくい複合条件(相対速度・進入角度・後方サポート人数の組み合わせ等)を提案できるかを実証的に検証する
2. 性能(F1)と解釈可能性(専門家評価)を分離して評価する枠組みを提示する
3. 1v1デュエル判定というタスクへの初適用を通じて、LLM×データ最適化ハイブリッド手法(FunSearch/EoH/LLM-SR等の系譜)のサッカー戦術領域での応用可能性を示す
